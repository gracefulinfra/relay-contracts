# A Docker Compose dev stack alongside the k3d platform

## Context and Problem Statement

Decision A13 made k3d the local cluster, and P0-05 built the whole platform on it through GitOps. That
is right for demonstrating the architecture: Argo CD, Argo Workflows (A7), CloudNativePG backups, the
Gateway, and the portability rehearsal all need Kubernetes. It is heavy for the inner loop of app
work, though: about 4.5 GiB and 1.5–5 minutes to start. It also cannot share the laptop with much
else, because the Docker VM has 7.75 GiB. On 2026-09-28 the owner asked for a local setup that is
"cleaner and easier to stand up", and chose to add Docker Compose rather than replace k3d.

## Decision Drivers

- Keep every U decision. A7 (Argo Workflows) and the GitOps parity of P0-05 and P0-07 need
  Kubernetes, so Compose cannot replace k3d.
- A fast, small inner loop for Phase 1 apps (relay-api, relay-site, relay-admin).
- No drift: the dev stack must behave like the platform where apps can tell the difference.
- Laptop footprint: the stack must be small (owner feedback, 2026-09-28).

## Considered Options

- **A. A Compose dev stack alongside k3d.** Compose for the backing services; k3d for everything that
  needs Kubernetes.
- **B. Compose only.** Drop k3d.
- **C. k3d only.**

## Decision Outcome

Chosen option: **A**. It is the only option that keeps U decision A7 and the tested GitOps and
portability path while giving a start in seconds.

- **`make dev`** in relay-infra (`compose/compose.yaml`, `scripts/dev.sh`) starts PostgreSQL 17.11,
  SeaweedFS 4.47, and Keycloak 26.7.4. `PROFILE=observability` adds the OTel Collector, Tempo,
  Prometheus, and Grafana. `make up` stays the k3d platform.
- **Parity where apps can see it.** It uses the same versions as the platform (the version matrix),
  the same buckets and per-consumer S3 identities and scopes (`S3_IDENTITIES`), **the same Keycloak
  realm files** (TOTP required), and the same telemetry routing and datasource uids.
  `make dev-smoke` checks the same guarantees as the platform smoke test for these services, and a
  `dev-stack` CI job runs it on every relay-infra PR.
- **Secrets** are generated by `scripts/dev.sh` into `~/.relay-local/dev/.env` (mode 600), never in
  git (ADR 0007's rule). Every port binds 127.0.0.1.
- **The definition of done does not change.** A slice's demo must still work on k3d (`make up`). The
  dev stack is for developing, not for acceptance evidence, unless a prompt says otherwise.

### Consequences

- Good, because app work starts in about 15 seconds on about 0.7 GiB (1.2 GiB with telemetry),
  instead of minutes and 4.5 GiB.
- Good, because building it found a real bug. The first CI run of the P0-07 rehearsal failed: on
  Linux, SeaweedFS's non-root user cannot read bind-mounted mode-600 secrets, which Docker Desktop on
  macOS hides. Both stacks now pass those files through an env file instead.
- Bad, because image pins now live in two places (the Compose file and the charts). A `make test`
  consistency check is a relay-infra follow-up (P1-01).
- Bad, because the dev stack has no Argo Workflows. P1-05 and P1-06 work that dispatches media jobs
  needs k3d.
- Neutral: the dev stack and k3d do not fit the reference laptop at the same time. One is stopped
  before the other starts.

### Confirmation

- relay-infra `make dev-smoke` (18 checks with the observability profile), locally and in the
  `dev-stack` CI job.
- `docs/laptop-profile.md` records the dev stack's memory and start times.

## Pros and Cons of the Options

### B. Compose only

- Good, because it is the simplest local setup.
- Bad, because it breaks U decision A7 (Argo Workflows needs Kubernetes), the GitOps layout rule of
  P0-05, and the tested P0-07 restore path, and it would need the owner to change U decisions.

### C. k3d only

- Good, because there is a single environment.
- Bad, because the inner loop stays at minutes and about 4.5 GiB, which the owner found too heavy.
