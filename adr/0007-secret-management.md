# Secrets reach workloads through External Secrets Operator

## Context and Problem Statement

`01-CONVENTIONS.md` says that secrets never go into git in plaintext, that local secrets are generated by a
script and never committed, and that P0-05 chooses the initial secret mechanism (P1-19 hardens it and
tests rotation). The mechanism has to work on a laptop with no cloud account, and it has to carry over to
the `provider-a`/`provider-b` environments (decision A5) without changing any application manifest.

## Decision Drivers

- Nothing secret in git, not even in encrypted form, so no key custody question exists for a public repo.
- One manifest shape for every environment: only the backend differs by provider (the A5 isolation rule).
- A realistic rotation story for P1-19: the source value changes and workloads pick it up.
- A small footprint on an 8 GB laptop profile.

## Considered Options

- External Secrets Operator (ESO), with a script-seeded Kubernetes namespace as the local backend
- SOPS + age, decrypted in Argo CD (KSOPS or helm-secrets)
- Sealed Secrets
- Plain Secrets applied by a script, outside GitOps

## Decision Outcome

Chosen option: **ESO with a script-seeded local backend** (owner decision **U**, 2026-09-26).

- Every workload secret is an `ExternalSecret` (or `ClusterExternalSecret`) that reads the single
  `ClusterSecretStore` named `relay-secrets`.
- `envs/local` points that store at ESO's `kubernetes` provider, which reads the `relay-secret-source`
  namespace through a ServiceAccount that can read Secrets only there. `scripts/secrets.sh` fills that
  namespace with generated values. It is idempotent: an existing value is never replaced by accident.
- Values that must outlive the cluster (the local CA the developer trusts once) are kept in
  `~/.relay-local`, outside every repository.
- Provider overlays replace only `ClusterSecretStore.spec.provider` with their secret manager or a
  KMS-backed Vault-API endpoint. Values are loaded into that backend out of band.
- The GHCR pull secret (ADR-0004) is a `ClusterExternalSecret` that is delivered to namespaces labelled
  `relay.dev/ghcr-pull=true`.

### Consequences

- Good, because git holds no secret material in any form, and provider overlays change one resource.
- Good, because rotation is "change the source, ESO refreshes", which is what P1-19 needs to test.
- Bad, because ESO adds three pods, and locally `relay-secret-source` is a single point of trust inside
  the cluster. Anyone who can read Secrets there can read everything. P1-19 reviews that RBAC.
- Bad, because a fresh cluster generates fresh credentials. Local data never outlives its cluster, so this
  is acceptable locally.
- Neutral: SOPS and Sealed Secrets stay available if a provider has no usable secret manager, but adopting
  either needs a new ADR.

### Confirmation

`relay-infra` `scripts/smoke.sh` checks that `ClusterSecretStore/relay-secrets` and the ExternalSecrets are
Ready. `make test` renders every overlay, and a review rule keeps `platform/` free of `Secret` manifests
that carry data. P1-19 adds a rotation test.
